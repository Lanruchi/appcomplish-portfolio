Create or complete a project case study using the compact standard in `docs/conventions.md`.

Usage: `/project <slug>` — e.g. `/project s3-static-website`.

0. Read the two reference pages first, `src/projects/s3-static-website.html` and `src/projects/s3-cicd-pipeline.html`, and match their structure, tone, callouts, table style, diagram style and length (about 600–800 words). New pages must read like siblings of these, not like a different author.
1. If `src/projects/<slug>.html` does not exist, copy `docs/templates/project-case-study.html` to it. If it exists, read it and list which parts are missing or still contain `TODO:`.
2. Interview the user ONE part at a time, in this order. Offer a short draft from what the conversation already established, and let the user edit it. Never invent facts, prices, or measurements — ask, or write "Not available".
   - Business Requirement (the need, why now and the requirements in one short paragraph, then the design question) · At a glance (Key decision, Stack incl. region, Monthly cost, Status; a Source row with the GitHub link for CI/CD pages) · Figure (one diagram, a short caption, an optional Proof line; an architecture "coming soon" slot only if an image will follow, none on CI/CD pages) · Problems I Hit and How I Fixed Them (real problems only; each is a red `callout--problem` with Trying to, What happened, Why, then a green `callout--fix` with numbered steps that name where to click; omit if nothing went wrong) · Design Considerations (run `/concepts <slug>`; the Cost row holds the estimate, rejected AWS options and pricing links).
   - Table rows that do not apply may say "n/a — <reason>". Unknown values: write "Not available" and say why. Never invent problems, prices or measurements.
3. Writing rules for every part you draft: be explicit (full service names on first use, e.g. "Amazon S3 bucket", "IAM role", spell out acronyms once); say WHY in captions, decisions and table rows; use plain language a beginner can follow; state only what was built, seen or sourced — no hypotheticals, no non-AWS comparisons, nothing the author could not defend in an interview; mask account and repository ID numbers as `xxxxxxx`; state each fact once.
3b. Cost rules: name at least two AWS options; estimates are fine; link each figure's source (AWS pricing page or https://calculator.aws/).
4. Write each approved part into the file, keeping the template's markup and classes. Update the card on `src/projects.html` (and `src/index.html` if featured), add the page to the folder tree in `README.md`, and link related case studies to each other.
5. Finish by listing remaining required gaps and running `/changes`. Then `/review` must run (Skill tool) and be shown before any commit is proposed. Do not stage, commit or push.
