What I Built

A static portfolio website hosted entirely on AWS — no servers, no containers, no runtime to manage. The domain appcomplish.click is registered through Route 53 and resolves to an S3 bucket configured for static website hosting.

Phase 1 (complete): S3 bucket + Route 53 DNS + public website endpoint live.

Phase 2 (in progress): CloudFront distribution in front of S3, HTTPS via AWS Certificate Manager, and AWS WAF for basic origin protection.

Why This Approach?

A static site on S3 has essentially zero operational overhead. There is no web server to patch, no process to restart, no ASG to manage. For a portfolio site that serves HTML, CSS, and JavaScript, that's the right level of complexity.

S3 also makes the infrastructure transparent — you can see exactly what the bucket policy allows, exactly which files are served, and the cost is single-digit dollars per month for low traffic. That visibility is useful when you're learning: fewer moving parts means clearer cause and effect.

Key Decision
S3 static hosting over a VPS or EC2 instance. A $5/month Lightsail instance would also work, but it introduces a Linux server, a web server daemon, and ongoing patching — none of which add value for a static site.

Alternatives I Considered

  • EC2 / Lightsail + Nginx — More control, but unnecessary complexity for static content. Server-side patching becomes your responsibility.
  • Vercel / Netlify — Faster to set up, great DX, but this project is about learning AWS primitives. Using a managed platform would skip the skills I'm trying to build.
  • AWS Amplify — Abstracts S3 + CloudFront nicely, but again hides the underlying services. Understanding the pieces separately first makes Amplify more meaningful later.
  • Elastic Beanstalk — Overkill for static content; designed for application servers.

Tradeoffs

  • No HTTPS on S3 endpoint alone — S3 static hosting serves HTTP. CloudFront is required to get HTTPS on a custom domain. This is a two-step setup, not one.
  • No server-side logic — Dynamic features (contact forms, auth, API calls) require additional services: API Gateway, Lambda, or a third-party form provider.
  • Cache invalidation cost — CloudFront charges after 1,000 invalidation paths per month. For a frequently updated site, a versioned file naming strategy (style.v2.css) is cleaner than invalidating on every deploy.
  • ACM certificate must be in us-east-1 — Even if your S3 bucket is in another region, the ACM cert for CloudFront must be provisioned in us-east-1. This surprises most people the first time.

What Would Break at 10× the Scale?

Realistically, a portfolio site won't hit scale limits. But the pattern extends to real products, and it's worth thinking through:

  • CloudFront handles it. A CDN in front of S3 means 10× or 100× traffic is just more edge cache hits — S3 itself barely sees the load.
  • What actually breaks is dynamic content. If this were a web app — user accounts, orders, a product catalog — the S3 layer stays fine but your API, database, and session management need rethinking at scale.
  • Build pipeline. Manually uploading files to S3 breaks the moment there's a team or frequent deploys. CI/CD via GitHub Actions + aws s3 sync is the fix.

What I'd Do Differently

Start with Terraform from day one. Clicking through the console is fine for learning, but the moment you want a second environment (staging vs production) or need to rebuild from scratch, manual steps don't scale. IaC makes the infrastructure self-documenting and repeatable.

I'd also set up a CI/CD pipeline immediately — even a simple GitHub Actions workflow that runs aws s3 sync and invalidates the CloudFront cache on push to main. Deploying by hand is the kind of friction that slows down iteration.
