CI/CD to S3 with GitHub Actions and OIDC

Built: October 2026
Business Requirement

I update this portfolio often while I learn, and uploading files by hand in the AWS console is slow, easy to forget and leaves no record. Every approved change must go live automatically (CI/CD, short for continuous integration and continuous delivery), with no AWS keys stored where they could leak, a preview before anything changes, and access limited to one bucket.

How would you deploy a static website like this?

Key decision
OpenID Connect (OIDC) role in AWS Identity and Access Management (IAM), no stored keys
Stack
GitHub Actions, AWS IAM, Amazon S3 bucket in us-east-1
Monthly cost
$0 for the pipeline (estimate)
Status
Live, auto-deploy on
Source
deploy.yml in the appcomplish-portfolio repository on GitHub

Problems I Hit and How I Fixed Them

My workflow has to log in to AWS and copy the website files into the S3 bucket. Three things went wrong on the way.

Problem 1

GitHub could not log in to AWS
Trying to: let the workflow log in to AWS without storing any AWS keys. GitHub sends a signed token that names my repository, and the IAM role's trust policy (its list of who may use it) says which names it accepts.
What happened: the run failed with Not authorized to perform sts:AssumeRoleWithWebIdentity.
Why: the sub (subject) line in my trust policy used the plain name, repo:nuru-adeniyi/appcomplish-portfolio:environment:production. GitHub was sending the name plus ID numbers, repo:nuru-adeniyi@xxxxxxx/appcomplish-portfolio@xxxxxxx:environment:production. They did not match, so AWS refused.

Fix
  1. Find what GitHub actually sent. AWS CloudTrail → Event history → filter Event name = AssumeRoleWithWebIdentity (region us-east-1) → open the failed event → read userIdentity → userName. That is the sub line GitHub sent: repo:nuru-adeniyi@xxxxxxx/appcomplish-portfolio@xxxxxxx:environment:production.
  2. AWS IAM → Roles → my deploy role → Trust relationships → Edit.
  3. In the sub line, replace the plain name with exactly what GitHub sends.
Problem 2

The login worked, but AWS refused to touch the bucket
Trying to: copy the website files into the S3 bucket, now that the login worked.
What happened: the run failed with no identity-based policy allows s3:ListBucket.
Why: a new IAM role can do nothing until it is given permissions.

Fix
  1. AWS IAM → Roles → my deploy role → Add permissions → Create inline policy.
  2. Allow it to list, add and delete files in this one bucket only.
Problem 3

Merged changes did not show on the live site
Trying to: see the changes from a merged pull request on the live website.
What happened: the deploy succeeded, but the site still showed the old pages, even in a private browser window. The response header said X-Cache: Hit from cloudfront.
Why: Amazon CloudFront keeps cached copies of each page. My deploy only copied files to S3, and nothing told CloudFront that they had changed, so it kept serving its old copies.

Fix
  1. CloudFront → Distributions → copy the distribution ID.
  2. AWS IAM → Roles → my deploy role → Add permissions → Create inline policy: allow cloudfront:CreateInvalidation on that one distribution.
  3. GitHub → Settings → Environments → production → Variables: add CLOUDFRONT_DISTRIBUTION_ID.
  4. Add a workflow step after the S3 sync that runs aws cloudfront create-invalidation --paths "/*". It is skipped on a dry run.
  5. Merge. The step turned green, and the live pages then returned X-Cache: Miss, meaning CloudFront fetched fresh copies.

Design Considerations

CategoryDecisionStatus
Requirements & workloadOne maintainer, a few merges a week, one repository. A pull request merging into main publishes src/.Addressed
Scalability & performanceOne deploy at a time. aws s3 sync re-uploads every file on each run, which is fine for a small site.Addressed
Availability & fault toleranceThe site keeps serving if the pipeline is down, and a repository variable pauses deploys. Rolling back by reverting the commit is untested. The pipeline depends on GitHub.Partly addressed
Data & consistencyn/a — static files only; Git is the source of truth.n/a
SecurityAn OIDC role instead of stored keys: a leaked key works until someone notices, while an OIDC login expires in about an hour. The role trusts only this repository, the production environment and main, and reaches one bucket. It can also clear the cache of one CloudFront distribution.Addressed
ObservabilityEach run logs every upload and delete. Failure alerts are missing.Not addressed yet
Deployment & DevOpsDry run, real run, then auto-deploy. --delete removes anything not in Git, and no link check runs first. The role was made by hand. Next: Terraform, pin actions to commit SHAs with Dependabot, and a link check. Each real deploy clears the CloudFront cache.Partly addressed
Cost & trade-offs$0 for the pipeline (estimate); GitHub Actions is free for public repositories. Rejected: stored access keys, because a long-lived key can leak; AWS CodePipeline and CodeBuild, $0–1 plus build minutes and more services to set up; EC2 with SSH, about $8 or more and a server to patch for static files; AWS Amplify Hosting, which hides the pieces I wanted to learn.
