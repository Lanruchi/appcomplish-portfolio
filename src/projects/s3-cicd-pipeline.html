CI/CD to S3 with GitHub Actions and OIDC

Built: October 2026 · Bootcamp: AWS Solutions Architect
Business Requirement

I update this portfolio often while I learn, and uploading files by hand in the AWS console is slow, easy to forget and leaves no record. I want every approved change to go live automatically (CI/CD, short for continuous integration and continuous delivery) without storing AWS keys anywhere they could leak.

How would you deploy a static website like this?

Goal
Publish static-website changes automatically and safely
Key decision
OpenID Connect (OIDC) role in AWS Identity and Access Management (IAM), no stored keys
Stack
GitHub Actions, AWS IAM, Amazon S3 bucket in us-east-1
Who
Me, the only maintainer, and the workflow calling AWS
Monthly cost
$0 for the pipeline (estimate)
Status
Live, auto-deploy on
Summary
A merge to main deploys this static website to an Amazon S3 bucket through GitHub Actions. The workflow logs in to AWS with OIDC, so no AWS access keys are stored. It costs nothing, previews changes with a dry run, and can be paused with one variable. For a static website this beats Amazon Elastic Compute Cloud (EC2) virtual servers, CodePipeline and stored keys; a dynamic app would change that answer.

Figure 1 — Why this works for a static website: it is only files, so one copy command is the whole deploy and no server has to be started. A dynamic app (server-side code, a database) would need a pipeline that builds and releases an application, often onto Amazon Elastic Compute Cloud (EC2) virtual servers or containers.

How It Works

  1. A pull request changing src/ merges into main.
  2. The workflow starts in the production GitHub environment, which only allows main.
  3. GitHub issues a signed token naming the repository and environment.
  4. AWS Security Token Service (STS) checks it against the IAM role's trust policy and returns temporary credentials.
  5. aws s3 sync src/ --delete makes the S3 bucket match the src/ folder.
Key Decision
An OIDC IAM role over stored AWS access keys. A leaked key works until someone notices; an OIDC login expires in about an hour and only works for this repository.

Problems I Solved

  • "Not authorized to perform sts:AssumeRoleWithWebIdentity" — my repository uses an immutable subject with numeric IDs, but the IAM trust policy used the plain name. I read the real format from the GitHub API and fixed the policy.
  • "no identity-based policy allows s3:ListBucket" — the login worked, but the role had no permissions yet. I added a policy limited to this S3 bucket.
  • Dry run impossible before the first merge — a manual run needs the workflow on main, and merging would have started a real --delete deploy. I added an AUTO_DEPLOY switch, merged safely, dry-ran, then turned it on.

Proof: the dry run listed 10 uploads and 1 delete (an old sample page). After the real run, the main pages and the stylesheet returned 200 and the deleted page returned 404.

Limits and Next Steps

  • Depends on GitHub. If Actions is down I deploy by hand; the live site is unaffected.
  • --delete is blunt, and nothing is tested yet. It removes anything in the S3 bucket that is not in Git, and no link or HTML check runs before a deploy.
  • At 10× the scale: many sites need reusable workflows, large S3 buckets make sync slow, and several environments need separate IAM roles and buckets.
  • Next: create the IAM role with Terraform, pin the actions to commit SHAs with Dependabot, add a link check and failure alerts.
